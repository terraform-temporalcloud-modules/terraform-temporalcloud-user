# Tests

Not usage examples — see [examples/](../examples) for those.

| Path | Runs on | Credentials |
| --- | --- | --- |
| `local/` | every pull request | no |
| `*.tftest.hcl` | on demand, weekly, and on every merge to `main` | **yes** |
| `setup/` | fixture for `*.tftest.hcl` | yes, when its namespace gate is on |
| `liveness/`, `orphan-check/` | fixtures for the scripts CI runs around the suite | yes |

`local/` passes every module input and references every output, so `terraform validate` fails there as
soon as the variable surface changes.

`*.tftest.hcl` applies against a real Temporal Cloud account. That is the only way to catch the API
rejecting a configuration that type-checks, and it is why the suite creates real users rather than
planning them.

## These tests create real users

**`terraform test` here invites real account members.** Each run creates a pending user, changes its
access several times, and destroys it.

What makes that safe is the address, not the absence of an apply:

- Every address is generated by `setup/` on **`example.com`**, which
  [RFC 2606](https://www.rfc-editor.org/rfc/rfc2606) reserves. The domain has no MX record and cannot
  be given one, so the invitation Temporal Cloud sends is undeliverable and no human is ever contacted.
- Every applying file asserts that domain in its `setup` run block, before anything is created. A
  failed `run` block makes every later one **skip**, so repointing `test_email_domain` at a deliverable
  domain stops the suite rather than mailing a stranger.
- Nothing hardcodes an address. Both wrapper addresses are derived from the fixture's local part, so
  they inherit the domain and the prefix rather than restating them.

What is real regardless of the domain: the user occupies an account seat from create until destroy, and
it is a genuine account member for the length of the run. Point the suite at a scratch account.

## What each file covers

| File | Covers | Applies |
| --- | --- | --- |
| `user.tftest.hcl` | Create one user; change its `account_access` in place; add a `namespace_accesses` grant, change its permission, then revoke it. Asserts `user_state` on the way | yes |
| `wrappers.tftest.hcl` | The `wrappers` submodule: two users from one call, with a per-item override of the shared default | yes |
| `disabled.tftest.hcl` | `create_user = false` creates nothing and every output falls back | yes, creating nothing |
| `precondition.tftest.hcl` | `admin` combined with `namespace_accesses` is refused by the module's precondition | no — see below |
| `validation.tftest.hcl` | Each variable validation refuses the value it is meant to refuse | no — see below |

### Why two files stay plan-only

`precondition.tftest.hcl` and `validation.tftest.hcl` assert that a configuration is **rejected**. A
rejection has no apply to run: the failure happens while Terraform is building the plan, so
`command = plan` is not a weaker form of coverage there, it is the only form. Do not convert them.

## One user, updated across run blocks

`user.tftest.hcl` creates a single user and updates it, rather than creating one per case. Run blocks
share state within a file, so a later block with different variables is an update — which is also what
proves the module updates in place instead of replacing.

Two rules the coverage depends on:

- **`email` forces replacement**, so it is held constant across every block. Changing it would revoke
  the previous address and send a fresh invitation, which is a destroy-and-recreate rather than an
  update.
- **Identity continuity is asserted against the previous block's `user_id`**, never against a value the
  same block passed in. `output.user_email == var.email` holds even when the user was destroyed and a
  replacement invited under the same address; only the ID tells the two apart.

## Why the namespace fixture is gated

`namespace_accesses` needs a namespace that exists: Temporal Cloud rejects an ID that does not name one
in the account, so a placeholder cannot stand in.

`setup/` therefore creates a throwaway namespace, behind `create_namespace_fixture`, off by default.
The `setup_namespace` run block switches it on **after** the account-access coverage has run. That
placement is deliberate: creating a namespace is the one thing in the fixture that can fail for
account-specific reasons — a namespace quota, or a region the account is not entitled to — and a failed
run block makes every later one skip. Sitting where it does, such a failure costs the namespace
coverage only, never the `account_access` lifecycle.

The last namespace block revokes the grant again, so by teardown the user holds nothing against the
fixture namespace and the two can be destroyed in either order.

## What is covered on apply, and what is not

| Input | Coverage |
| --- | --- |
| `create_user` | Apply, both values |
| `email` | Apply. Held constant within a file, so its replacement behaviour is not exercised — replacing means a second invitation |
| `account_access` | Apply, created as `read` and updated to `developer`. `admin` is plan-only via the precondition; `owner` cannot be created at all, and `financeadmin` / `metricsread` are unexercised |
| `namespace_accesses` | Apply — added, permission changed, revoked, against a real namespace |
| `timeouts` | Apply, passed on every block |
| `account_access_custom_roles` | **Not covered.** `local/` only |

| Output | Coverage |
| --- | --- |
| `user_id` | Apply, and it carries the update-versus-replace assertions |
| `user_email`, `user_account_access`, `user_namespace_accesses` | Apply, round-tripped through the API |
| `user_state` | Apply. Asserted to be `activating` or `active`, so the failure states would fail the run |
| `user_account_access_custom_roles` | Apply, but only ever as an empty set |

### `account_access_custom_roles`

It needs a `temporalcloud_custom_role` to point at, and a role ID that does not exist is rejected, so a
placeholder cannot be applied. Creating one is not possible with the shared test key: custom role
administration [defaults to the Account
Owner](https://docs.temporal.io/cloud/manage-access/custom-roles#delegating-custom-roles), and this key
is refused with `PermissionDenied` — the same wall
[`terraform-temporalcloud-custom-role`](https://github.com/terraform-temporalcloud-modules/terraform-temporalcloud-custom-role)
has hit.

A plan-only run block with a placeholder ID would prove only that the module can serialise a string,
which `local/` already covers, so it was removed rather than kept as decoration. When an Account Owner
key is available, add a gated custom role to `setup/` alongside the namespace and a run block that
grants and revokes it.

## Access the suite needs

`TEMPORAL_CLOUD_API_KEY` is the only credential, supplied to CI as an organisation secret of that name.
Beyond the key existing, the **account behind it** must be able to:

| Capability | Needed by | If missing |
| --- | --- | --- |
| Create and delete users | `user.tftest.hcl`, `wrappers.tftest.hcl` | the applying suite fails outright |
| Two free account seats, against a [limit of 300 by default](https://docs.temporal.io/cloud/limits) | the same two files — one user, then two at once in the wrapper | the create fails on a quota, for reasons unrelated to this module |
| Create a namespace in at least one region | `setup/` with its gate on, and `orphan-check/` | the namespace blocks of `user.tftest.hcl` fail; everything before them is unaffected, which is why the gate exists |

## Running the apply tests

```bash
export TEMPORAL_CLOUD_API_KEY="<key for a scratch account>"
terraform init
terraform test -verbose
```

Point them at a scratch account: they create and destroy **real** account members.

Without a key, every run block is skipped — a cheap way to confirm the test files parse:

```text
Failure! 0 passed, 0 failed, 17 skipped.
```

A syntax or reference error looks different: it names a file and a line rather than reporting a
connection failure.

## Cleaning up leftovers

`terraform test` destroys what it created, including after a failed assertion, but a cancelled or
crashed run can orphan something — and here an orphan is a real pending account member holding a real
seat. CI therefore runs `scripts/check-orphans.sh` after the suite, always, including when the tests
fail, since that is when something is most likely to have been abandoned.

```bash
scripts/check-orphans.sh
```

It reads `temporalcloud_users` **and** `temporalcloud_namespaces`, so it covers both resource types the
suite creates. Unlike some of the sibling modules, nothing this suite creates is invisible to it.

| Prefix | Created by |
| --- | --- |
| `yulei-tftest-usr-<random>@example.com` | users, from `*.tftest.hcl`; the wrapper suffixes the local part with `-ana` and `-ben` |
| `yulei-tftest-usr-<random>` | the throwaway namespace in `setup/` |
| `yulei-tflocal-*` | `local/`, only if applied by hand — CI never applies it |

`setup/` and `orphan-check/` must agree on that prefix. They are the only two places it appears; change
one and the check silently stops seeing leftovers.

Anything matching those prefixes that no live run owns can be deleted. Confirm each address belongs to
the suite before deleting a user — removing one revokes that person's access.

The `examples/` directories are not covered by the prefix; they use `developer@example.com` and
`auditor@example.com`. Example code is published to the Terraform Registry, so it carries no
test-specific naming. Check for those separately if you have applied an example by hand.
